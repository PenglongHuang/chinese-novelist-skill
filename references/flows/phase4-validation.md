# 第四阶段：自动校验与修复

**主 Agent 专用。** 进入本阶段时，所有写作 worker 已结束。主 Agent 只调用校验脚本、派遣原写作 worker、收集结果和复检，不亲自处理章节问题。全程不向用户请求确认。

## 1. 初始化校验

读取 `02-写作计划.json`，将项目 `status` 更新为 `"validating"`。

## 2. 脚本校验

按 skill 安装目录的绝对路径调用：

```bash
node "{skillBaseDir}/scripts/validate_project.mjs" "{项目目录绝对路径}" --json
```

脚本按计划逐章检查状态，调用原字数脚本读取正文并统计，字数口径不变，下限取本书 `minWordsPerChapter`（缺省 3000）。不单独检查文件存在性，不检查章节摘要。

脚本回填每章 `wordCount`、`wordCountPass`、`validation`（本次结论、问题类型和时间），保留原章节 `status`、`retryCount` 及其他字段；不新增 `lastError`。重复校验不增加修复次数。

| 类型 | 给 worker 的处理建议 |
|---|---|
| STATUS_NOT_FINAL | 核对实际完成情况，补齐未完成步骤和状态，不直接重写已有有效正文 |
| CHAPTER_FAILED | 核实原执行结果并处理失败原因，不能仅凭字数达标清除失败 |
| WORD_COUNT_LOW | 保留已有正文，按文风和扩充指南定向扩充 |
| READ_ERROR | 解决读取或脚本执行问题后复检，不按零字扩充或重写正文 |

读取失败时字数与通过标记设为 null，校验结论为 error；这是脚本错误。JSON 的 `tasks` 按章合并失败类型、动作建议和实测证据。退出码：0=全部通过，1=校验未通过，2=读取或脚本错误。计划损坏等无法校验的错误直接返回 error，不覆盖计划。

## 3. 汇总与派遣

- 全部章节状态为 completed 且字数达标：主 Agent 将项目设为 completed，报告结果。
- 有未通过项：主 Agent 将各章的 `tasks` 派回原写作 worker。原 worker 无法继续时，新建 worker 接收相同上下文；同一章的问题合并为一次任务。
- 脚本整体失败而没有章节任务时，派 worker 处理该脚本错误，解决后重新校验，不推测正文需要改写。

派遣时给 worker：项目及章节路径、失败类型、实际/要求字数、动作建议、`chapter-checklist.md` 及适用的文风/写作指南。不要让 worker 执行本文件的全书流程。

**worker 修复范式：**

> 先核实问题，再执行建议动作。仅处理本章必要步骤，不机械重跑整章创作；可读取必要前后文，不修改其他章节。实际处理时将本章设为 in_progress，完成后设 completed，未解决则设 failed。用 Edit 更新自己章节的记录，冲突时报错后重读再 Edit，不使用状态更新脚本或锁。每次创作修复尝试结束后将本章 retryCount 加1，成功失败均计一次；单纯复检、读取故障处理不计创作次数。不新增 lastError，失败原因在返回结果中说明。返回处理结果、改动文件、检查结果和剩余问题，不向用户提问。

## 4. 最多三轮修复

首次校验后，每轮只派遣未通过项；全部 worker 返回后，主 Agent 调用脚本复检全书，已通过的章节不重复派遣。全书最多三轮；各章 retryCount 只记录该章实际执行的创作修复尝试。

三轮后仍未通过：主 Agent 将项目设为 needs_attention，保留校验标注，报告未通过章节或脚本问题，结束本轮执行。不能标 completed，也不保持为仍在执行的 validating。

## 5. 报告

全部通过时，将作品信息追加到 `user-preferences.json` 的 `creationHistory`，报告作品名、章数、实测总字数和项目路径；仍有问题时报告“待处理”、失败类型及已执行轮次，不宣称完稿。后续恢复时，从校验和未通过项继续。
